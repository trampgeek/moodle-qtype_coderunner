# Implementation notes

Technical details and gotchas found while checking the design against Moodle and CodeRunner code (Moodle 5.1, CodeRunner 5.10.8). They are for whoever implements the design, not for discussion with colleagues. Items marked *to check* were read from the code or inferred, not tested. File paths are relative to Moodle's `public/` directory. The prototype manager plugin is called `local_<manager>` below; its real name is still to be chosen.

## Storage

- **Prototypes table.** One row per prototype: id, name, `courseid` (`SITEID` for site prototypes), stable identifier, current version number, a copy of the current version's parent prototype id (for queries such as listing children), built-in flag, created and modified times and users. Records the scope as a course only; there is no question-bank scope.
- **Stable identifier.** Generated once with `\core\uuid::generate()` when a prototype is created, and kept through export, backup and restore. It is not unique on a site: a restore or import that cannot use the original (for example because the user cannot use it from the restored course) creates a copy with the same identifier. So index it, but not as unique, and when several prototypes carry the identifier, prefer one in the target course, then a site prototype, then one in another course the user can use.
- **Names.** Unique across one course's prototypes plus all site prototypes. A unique index on (`courseid`, `name`) covers the course part; the clash with site prototypes, and for a new site prototype with every course, must be checked in code inside a transaction.
- **Versions table.** One row per saved version: prototype id, version number, parent prototype id (null for a root), the complete set of fields the prototype sets (JSON), commit message, user and time. The parent belongs to the version, not just the prototype, so a prototype whose parent was changed still shows its earlier versions correctly; resolution follows each version's parent id to that parent's current version. Each row is complete; diffs are computed for display. The prototype row's current version points into it.
- **Support files.** Stored through the file API in the manager's own component, with the version row's id as the item id. The file API deduplicates by content hash, so an unchanged file costs only a file record per version.
- **Questions.** `question_coderunner_options` gains the prototype id and the overrides JSON. The old option columns stay, unused at run time, until phase 4; a legacy reader keeps using them for migration and for legacy import and restore.
- **Field registry.** Every inheritable field is a registry entry in code with its type, default, merge rule (replace, merge by key, merge by filename) and form section. Resolution, both forms, export, backup and the migration check all work from the registry.
- **Resolved settings cache.** **Not in 6.0**; see decision 15 in the milestones document, which defers it until a measurement asks for it, because `questiondata` is an application cache and so already resolves each question once rather than once per attempt. The design, if it is ever built: a Moodle application cache keyed by the chain of version ids (the same string the attempt records), holding the resolved settings. Entries never go stale, because a version never changes, so no invalidation is needed except by pruning.

## Resolution and versions

- **Recording versions.** Set a qt\_var (for example `_prototypeversions`) in `start_attempt()`, alongside `_mtrandseed`, `_STUDENT` and `_QUIZ`. Its value is the chain from the root as id@version pairs, such as `37@41,412@7`.
- **Regrade does not call `start_attempt()`.** `question_attempt::regrade()` (`question/engine/questionattempt.php`) calls `start()` with the old first step's data and its existing step id. `start()` builds a new `question_attempt_step` and calls the behaviour's `apply_attempt_state()`, then replays the later steps through `process_action()`.
- **Detecting a regrade in `apply_attempt_state()`.** The step is not a `question_attempt_step_read_only` and `get_id()` is not null. Ordinary loads use `load_from_records()`, which builds read-only steps; in core's question engine only `regrade()` passes an existing step id. This is an internal convention, so add a unit test.
- **Refreshed versions persist.** In `question/engine/datalib.php`, `notify_step_added()` moves a step that has an id from the deleted list to the modified list, so `save()` overwrites the row with `update_question_attempt_step()`. A qt\_var set in `apply_attempt_state()` during a regrade is therefore saved.
- **`update_attempt_state_data_for_new_version()`** is called only when a regrade moves to a new question version, so it cannot detect prototype-only changes.
- **Existing parameter caching.** `template_params_json()` in `question.php` stores an md5 of the raw parameters and the evaluated JSON in qt\_vars (`_template_params_md5` and `_json`, and `_prototype__template_params_*`), and writes them only when the step is not read-only. It re-evaluates when the md5 differs.
- **Pruning.** The *Prune prototype history* script keeps the last N versions of each prototype plus every version named in any `_prototypeversions` qt\_var. Finding those needs one pass over `question_attempt_step_data` rows with that name; do it in a single recordset, not per prototype.
- **Pushing a version to attempts in progress.** Rewrite the old `id@version` pair in each affected `_prototypeversions` value with one bulk update of `question_attempt_step_data`, limited to the chosen quizzes' attempts whose `quiz_attempts.state` is `inprogress` or `overdue`. Previews and other modules that use the question engine need their own rule for "in progress" (for example the question attempt's latest state not finished); previews can simply be included. This writes step data behind the question engine's back; it is safe because the qt\_var is read on each load and never held in the session, but add a test that an attempt picks up the new version on its next action. Record each push (user, version, attempts affected) in the prototype's history.

## Backup and restore

- **No backup or restore settings for local plugins.** `backup_structure_step::add_plugin_structure()` (`backup/util/plan/backup_structure_step.class.php`) calls `backup_local_<name>_plugin::define_<element>_plugin_structure()` for every element it is attached to, with no UI setting. The plugin can read existing settings with `get_setting_value()`, such as `users`.
- **Attachment points used.** Course and question (`backup/moodle2/backup_stepslib.php`). Local plugins can also attach to module, section, grade item and grading areas, but with no question-bank scope the module point is not needed. Question types and `qbank_` plugins attach only per question.
- **Plan order.** `backup_plan_builder` adds the root task, the course task, the section and activity tasks, then `backup_final_task`. `course.xml` is written in the course task, before the activities annotate the `question_bank_entry` references they use. `questions.xml` is written by `backup_questions_structure_step` in the final task, after all annotations. So the course hook cannot tell which questions are included; prototypes needed by questions must be written by the question-level hook, `add_plugin_structure('local', $question, true)` in that step.
- **What each point writes.** The course point writes all of the course's prototypes, plus any ancestors they have outside the course other than built-ins. The question point writes, at the first question that needs it, each prototype in that question's chain not yet written, other than built-ins. Within each point, write parents before children.
- **Write each prototype once.** Record each written prototype id in `backup_ids_temp` under the manager's own item name (`backup_structure_dbops::insert_backup_ids_record()`), and skip prototypes already recorded, whichever point wrote them. Write each prototype's whole version history, its stable identifier, and its course id so restore can tell whether its course is part of the restore.
- **Which backup runs which hooks.** Quiz duplication and other single-activity backups do not write the course element, so only the question point runs; the duplicate lands in the same course and the restore maps every prototype back to the original by identifier. Course import ("Import from another course") and course copy are course backups.
- **To check on restore: precheck-mapped questions.** Whether question-level plugin paths are processed for questions that the prechecks mapped to existing questions rather than created. Plugins conventionally test the `question_created` mapping and skip otherwise (see `restore_qtype_plugin`). Because a prototype is written only with the first question that needs it, the manager must restore it whether or not that question is created.
- **Restore order.** *To check*: Moodle creates the restored questions in an early root-task step (`restore_create_categories_and_questions`), before the course task restores course-level plugin data. So questions can arrive before the prototypes they use, and a child at the course point can have its parent at the question point. Legacy backups have prototype questions anywhere.
- **Mapping each incoming prototype.** When the manager restores a prototype element, it decides at once which prototype it maps to and records old id → new id with `set_mapping()`: an available prototype with the same identifier (adding any versions it lacks), or a new prototype. A new one gets the restored course's id if its own course is the one being restored or belongs to another course, and also if it was a site prototype, since restoring a course must not create site prototypes. A name clash gets a new name such as `cosc131_scratchpad (2)`.
- **Linking after restore.** Questions and child prototypes store only the incoming reference during the restore: the old prototype id for a new backup, the prototype name for a legacy one. They are linked in the plugin's after-restore stage, once everything is loaded, using the recorded mappings or, for legacy backups, today's name rules over the course's prototypes (including those just restored) and the site prototypes. *To check*: which `after_restore_*` method runs for single-activity restores such as quiz duplication, where the course element is absent; a question-level `after_restore_question()` or a final step may be needed.
- **Questions from banks in other courses.** `backup_question_dbops::calculate_question_categories()` includes every category in the backed-up context, plus `question_category_partial` entries for categories elsewhere that hold annotated questions, with only those questions. On restore, `restore_dbops::restore_find_best_target_context()` matches module-level categories by stamp only against banks in the target course. `restore_move_module_questions_categories` (`backup/moodle2/restore_stepslib.php`) then either, on the same site with `mod/qbank:view` on the original bank, repoints the restored `question_references` to the original questions (the restored copies appear to be left behind), or creates a default bank with `question_bank_helper::get_default_open_instance_system_type()` and puts the copies there. Either way the questions keep working, because their prototypes map by identifier. Read from the code, not yet tested.
- **No way to ask the user during restore.** Prechecks (`restore_prechecks_helper`) call core functions only and are not pluggable. Messages logged with `$this->log(..., backup::LOG_WARNING)` reach the restore page only when `$CFG->debugdisplay` is on and the restore is synchronous (`backup/restore.php`); asynchronous restores, now the default, show nothing. Renamed prototypes must therefore be reported by a Moodle notification to the user who ran the restore.
- **Recoding attempt data.** `restore_qtype_plugin::recode_response($questionid, $sequencenumber, $response)` is called for every restored attempt step (`restore_questions_attempt_data_trait::questions_recode_response_data()` in `backup/moodle2/restore_stepslib.php`). Use it to rewrite the prototype ids in `_prototypeversions` through the prototype mappings; version numbers stay. Attempts are restored in the activity tasks, after the questions and course-level data, so the mappings already exist (*to check*).
- **Identity hash.** `restore_dbops` loads candidate questions from the database with `export_process` set, and the backup side goes through `convert_backup_to_questiondata()`, `define_excluded_identity_hash_fields()` and `remove_excluded_question_data()` in `restore_qtype_coderunner_plugin`. Exclude the prototype id from the hash (it differs between sites and is filled in late) and never run prototype resolution on either side. Convert legacy backups to the new storage form in `convert_backup_to_questiondata()`, because the conversion to overrides JSON changes the hash. A mismatch only creates duplicate questions; it loses nothing.

## Export and import

- **Export.** A question's Moodle XML holds its overrides plus its prototype's name and identifier. *Include prototypes* adds the chain (each prototype with only its current version); *Flatten* writes the resolved settings into the old columns' format so older CodeRunner versions can import it.
- **Refusing an import.** Resolve each question's prototype while the file is parsed (the qtype's `import_from_xml()`), and report a missing one with `$format->error()`. `qformat_default::importprocess()` (`question/format.php`) checks `importerrors` before writing anything when *Stop on error* is set, which is the default, so nothing is saved.
- **Within one file.** Prototypes in the file (*Include prototypes* or legacy prototype questions) must be resolvable at parse time, so collect them in a first pass over the parsed questions, or resolve against the file's own prototypes before the site's.

## Course deletion and permissions

- **Course deletion.** A prototype that other courses still use must be moved to site scope, renamed if its name clashes, and the administrators notified. Use the `pre_course_delete` callback or its Moodle 5 hook replacement (*to check* which is current). Prototypes no other course uses are deleted with the course, after its questions.
- **Capability checks.** Using a prototype from another course needs `qtype/coderunner:management` in that course. Check it in the picker and again on save, since the form can be submitted without the picker.

## Current lookup and inheritance (for migration and legacy import)

Today's name-based lookup is needed only once per question, during the migration, and for legacy imports and restores.

- `get_prototype()` in `questiontype.php` looks up the prototype by `coderunnertype` in the contexts from `prototype_contexts()`, and fails on zero or several matches.
- `get_question_options()` skips inheritance when `$question->export_process` is set.
- `set_inherited_fields()` treats null as inherit and turns blank strings into null; the new design drops that conversion.
- `get_files()` in `question.php` merges prototype support files with the question's own.

## Forms and the mockups

- **The mockups are illustrative, not a specification.** The two mockups (question form and prototype editor) show layout and interaction: section structure, the inherited/overridden display with *Revert to inherited*, change counts on section headers, help icons, the test case field switches, *Show all parameters*, *Show as JSON* and the grouped prototype picker. They deliberately omit many fields and must not be used to define the field set.
- **The field set comes from the current code.** Every field in `extra_question_fields_static()` and `noninherited_fields()` in `questiontype.php`, and every control in `edit_coderunner_form.php`, must appear in the new forms unless the design doc says otherwise. Fields easily missed because the mockups omit them include the template parameter controls (preprocessor language, evaluate per try, Twig all), *Hide check*, the stop button, feedback display (*Force show* and so on), template-uses-Ace, the test splitter and multiple-stdins settings, attachment settings, and UI parameters and sandbox parameters in the prototype editor.
- **Both forms render from the registry** through the shared editor component, so a field present in one is present in the other.
- **Template debugging** is the `showsource` column, and so an ordinary instance field of the registry. An earlier draft of this note called it a per-session author option that would stay outside the registry; it is neither (see M7's first increment).
- **Help strings.** Existing `_help` strings in `lang/en/qtype_coderunner.php` should be kept and attached to the corresponding registry entries; the mockups show the opening sentences of them.
- **Picker group "already used in this course".** Needs the prototype ids used by the course's CodeRunner questions: one query joining `question_coderunner_options` through `question_versions`, `question_bank_entries` and `question_categories` to the contexts of the course's banks and quizzes. Cache it per course for the session.

## Migration

- **Scale.** Plan for very large sites: one site has reported 410,000 questions in its question banks. Moodle keeps a `question` and a `question_coderunner_options` row for every version of every question, and every version must be migrated. Targets: a few minutes in total for 400,000 options rows, with steady progress shown throughout.
- **Check inside the upgrade step, not as an environment check (preferred).** The design doc leaves open how to guard against migration bugs. An environment check (`environment.xml` `CUSTOM_CHECK` at `level="required"`, run by `lib/environmentlib.php` from both the web and CLI upgrade) cannot show progress and runs several times (environment page, upgrade start, admin pages until the upgrade completes); at about a minute per 100,000 questions that is minutes per run on a large site, and administrators would assume a hang. Instead, make the comparison the first pass of the upgrade step itself, behind a `progress_bar`, before anything is written. If any question's old and new settings differ, throw an exception naming the first few questions and the total, before the savepoint is reached: the plugin's version in the database stays at 5.x, so the administrator can reinstate the previous code, the same outcome as a failed environment check. If all match, the second pass writes.
- **Read in bulk.** Stream all `question_coderunner_options` rows with one recordset query that joins each question to the course it belongs to (through `question_versions`, `question_bank_entries`, `question_categories` and the context path). Do not load questions one by one through `get_question_options()` or the question bank API: several queries per question, roughly half a minute for 5,000 questions and far too long for 400,000.
- **Resolve in memory.** Load all prototype questions once and keep them, old-style and converted, in memory, keyed for today's name rules (name plus the contexts `prototype_contexts()` would search), so each question's prototype is found by a lookup, not a query. Do the old name-based resolution, the conversion to overrides JSON plus prototype id, and the new id-based resolution in memory, and compare the results as arrays. Compare template parameters as merged JSON text before evaluation; never evaluate Twig or contact the sandbox.
- **Write in bulk.** One `update_record()` per row costs 1–3 ms, so 7–20 minutes at 400,000 rows. Instead insert the results in batches into a temporary table (`insert_records()` in chunks of a few thousand) and apply them with one `UPDATE … JOIN` per batch or overall; expect one to three minutes. Call `upgrade_set_timeout()` and update the progress bar between batches, so web upgrades do not time out.
- **Memory.** Stream questions, never hold them all; only prototypes and the per-batch results stay in memory.
- **Attempts are not migrated.** Existing attempts have no `_prototypeversions` qt\_var. Treat a missing value as version 1 of each prototype in the question's chain, the snapshot the migration creates, so the millions of attempt step rows on a large site need no change.
- **Storage growth.** Keeping the old columns until phase 4 duplicates each question's options as JSON. Most overrides are small, but a customised question carries its whole template, so a large site may grow by a few hundred MB until the old columns are dropped.
- **Measure first.** Write the comparison pass as a standalone CLI script and time it on a real large site before relying on these estimates; the same script can become part of the 5.x prototype health report, so large sites can run it before upgrading.
